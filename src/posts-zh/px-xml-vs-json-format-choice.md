2000 年前后，XML 是数据交换的默认选项，而 2010 年代 JSON 随 Web API 普及成为主流。时至今日，二者仍在不同领域扮演关键角色，技术选型时开发者常面临困惑，单纯讨论优劣已无意义。

本文旨在解决场景化选型难题，助你清晰判断在配置文件、API 交互与文档处理三大场景下，如何做出最合适的技术决策。文章将抛开抽象之争，聚焦于实际应用中的可操作性判断依据。

先说版本基线：XML 1.0 于 1998 年成为 W3C 推荐标准，2008 年发布第五版；JSON 由 Douglas Crockford 在 2001 年左右提出，2017 年发布 RFC 8259（STD 90）。YAML 1.2 于 2009 年发布，常作为两者之外的补充。具体细节以官方规范为准。

## 配置文件场景

XML 的强项是 schema 校验和命名空间。如果你需要严格约束结构，XML Schema（XSD 1.0 于 2001 年成为 W3C 推荐标准）能表达元素顺序、类型和出现次数。代价是冗长：一个简单的数据库连接配置，XML 往往要写十几行。

JSON 的配置文件更紧凑，但原生不支持注释。RFC 8259 明确禁止注释，实践中不少解析器宽容处理，但跨工具链时容易出问题。YAML 支持注释和锚点，适合人工维护，但缩进敏感、类型隐式转换（如 `on` 被解析为布尔值）是常见坑。

我的做法是：机器生成且需要严格校验的配置用 XML；手写且结构简单的配置用 JSON；需要注释和复用的复杂配置考虑 YAML，但必须配 schema 校验。

## API 场景

JSON 在 API 领域占优，主要因为浏览器原生支持 `JSON.parse`，且体积小。REST API 返回 JSON 已成惯例。XML 在 SOAP 和企业级集成（如 WS-Security）中仍有位置，但新项目很少首选。

如果你要设计一个 API，可以按以下步骤判断：

1. 确认消费端：浏览器和移动端优先 JSON；需要消息级安全或事务语义时评估 XML。
2. 定义数据契约：JSON 用 JSON Schema（2020-12 是较新版本），XML 用 XSD。两者都能做校验，但 JSON Schema 工具链更轻。
3. 处理扩展性：XML 命名空间允许混用词汇表；JSON 没有原生命名空间，通常靠字段前缀约定。
4. 测试兼容性：用目标语言的标准库解析，避免依赖非标准扩展。

## 文档场景

XML 在文档标记上根基深：DocBook、DITA、TEI 都基于 XML。XSLT 1.0（1999 年 W3C 推荐标准）和 XPath 能对文档做结构化转换。JSON 缺少等价的转换标准，虽然 JSONPath 有提案，但未形成统一规范。

如果你的文档需要多输出格式（HTML、PDF、EPUB），XML + XSLT 仍是成熟路径。如果只是存储结构化内容供前端渲染，JSON 更直接。

## 对照表：三个场景的关键差异

| 维度 | XML | JSON |
|------|-----|------|
| 注释 | 支持 | 不支持（RFC 8259） |
| 模式校验 | XSD、Relax NG | JSON Schema |
| 命名空间 | 原生支持 | 无原生支持 |
| 体积 | 较大 | 较小 |
| 文档转换 | XSLT、XPath | 无统一标准 |
| 浏览器解析 | DOMParser | JSON.parse |

## 选择决策表

| 你的场景 | 优先选择 | 理由 |
|----------|----------|------|
| 需要严格模式校验的配置 | XML | XSD 成熟，工具多 |
| 手写简单配置 | JSON | 紧凑，解析普遍 |
| 需要注释的配置 | YAML | 原生支持注释 |
| 公开 REST API | JSON | 浏览器友好，体积小 |
| 企业 SOAP 集成 | XML | WS-* 标准支撑 |
| 多格式文档发布 | XML | XSLT 转换链成熟 |
| 前端渲染数据 | JSON | 直接映射对象 |

## 我的两个实践建议

第一，不要为了统一而统一。我见过团队把原本用 XSD 校验的配置改成 JSON，结果校验能力下降，问题推迟到运行时才暴露。格式选择应服务于校验和工具链，而不是个人偏好。

第二，混合使用是常态。一个系统里 XML 做文档源、JSON 做 API 响应、YAML 做部署配置，完全合理。关键是每个环节明确契约，并写进文档。

## 常见问题

**问：JSON 能替代 XML 做配置文件吗？**
答：多数简单场景可以，但 JSON 不支持注释，且 JSON Schema 的表达能力在某些约束上不如 XSD。需要严格校验时，评估两者工具链后再定。

**问：YAML 是 JSON 的超集吗？**
答：YAML 1.2 声称是 JSON 的超集，但实际解析器行为有差异，比如重复键和特殊数值的处理。跨格式转换时以官方规范为准，并做往返测试。

**问：XML 命名空间在 JSON 里怎么处理？**
答：JSON 没有原生命名空间机制。常见做法是用字段前缀（如 `ns:field`）或嵌套对象模拟，但这只是约定，不具备标准层面的隔离能力。

**问：新项目应该选哪个？**
答：看消费端和校验需求。浏览器和移动端优先 JSON；需要文档转换或消息级安全时考虑 XML；需要注释的配置可评估 YAML。没有唯一答案，决策表可作为起点。
