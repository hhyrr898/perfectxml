W3C 于 1998 年 2 月发布 XML 1.0 推荐标准。本文旨在阐明为何这项近三十年前的技术至今仍在关键领域发挥作用，并帮助你在 2026 年的四个典型场景中从容应对 XML 相关任务。

XML 的核心价值在于其自描述性。它通过标签对数据赋予明确的结构与语义，实现了人类可读与机器可解析的统一。这种特性使其在特定领域，尤其是在需要长期存档、跨系统交换复杂数据时，依然具备不可替代的优势。

```xml
<order id="20260115-001">
  <customer>Ada</customer>
  <item qty="2">keyboard</item>
</order>
```

关键点在于 XML 只规定语法，不规定你用哪些标签。你可以自由发明 `<order>`、`<item>`，这正是 Extensible（可扩展）的含义。与之配套的还有一系列规范：命名空间（Namespaces，1999 年成为推荐标准）、Schema 校验（XML Schema 1.0 于 2001 年发布）、XPath、XSLT、XQuery。它们共同构成一个完整的数据描述与转换体系。

我第一次系统读 XML 规范时最大的感受是：它把"格式"和"语义"分得很开。XML 本身不告诉你 `qty` 是数字还是字符串，属性一律是文本；类型约束要靠 Schema 或 DTD 另行声明。这个设计既带来灵活性，也带来啰嗦，后面会具体说。

## 2026 年它还在哪些地方

### 配置文件

Maven 的 `pom.xml` 是最典型的例子，从 2004 年 Maven 2 起沿用至今。Java 生态里还有 Spring 的 XML 配置、Android 的布局与清单文件 `AndroidManifest.xml`、Tomcat 的 `server.xml`。这类场景的共同特点是：结构固定、层级浅、需要注释、偶尔要用 Schema 做 IDE 补全。

### SOAP 与企业系统集成

SOAP 1.1 于 2000 年提交 W3C，1.2 于 2003 年成为推荐标准。银行、电信、政务、ERP 之间的接口至今大量使用 SOAP over HTTP，配套 WSDL 描述服务契约、WS-Security 处理签名加密。这些系统生命周期长，改造代价高，所以 XML 会长期存在。

### 文档格式

Office Open XML（docx、xlsx）本质是 zip 包里的一组 XML 文件；ODF 同理；SVG 是 XML 的图形方言；RSS 与 Atom 是订阅格式。你解析一个 docx 的正文，实际就是在读 `word/document.xml`。

### 数据交换与行业标准

HL7 v3（医疗）、UBL（发票）、XBRL（财务报告）都用 XML Schema 定义了严格的行业词汇表。这些标准的价值不在格式本身，而在"所有人对字段含义有共识"。

## 一个对照表：XML、JSON、YAML 怎么选

| 维度 | XML | JSON | YAML |
| --- | --- | --- | --- |
| 类型系统 | 无内置类型，靠 Schema | 数字、布尔、null、字符串、数组、对象 | 同 JSON，另有日期等扩展 |
| 注释 | 支持 `<!-- -->` | 不支持 | 支持 `#` |
| 校验能力 | Schema、DTD、Schematron | JSON Schema | 较弱 |
| 命名空间 | 原生支持 | 无 | 无 |
| 人类可读性 | 标签冗余，较长 | 一般 | 缩进敏感，易读但易错 |
| 典型场景 | 企业契约、文档格式 | Web API | 配置与编排 |

我的经验是：需要跨组织约定字段、需要命名空间避免冲突、需要严格校验时，XML 仍是稳妥选择；纯内部配置和前端接口，JSON 与 YAML 更省事。

## 2026 年仍会遇到它的原因

第一是存量。企业里跑了十几年的 ESB、注册中心、报文网关不会因为新语言流行就重写。第二是契约文化。WSDL 加 Schema 能生成强类型客户端，这在多团队协作中省下大量沟通成本。第三是工具链成熟：XSLT 做格式转换、XPath 做精确定位、Schematron 做业务规则校验，这套组合至今没被完全替代。

我个人处理过最麻烦的一次故障，是一个属性值里混进了未转义的 `&`，导致整个报文在另一端解析失败。XML 的严格性在这里是优点也是痛点——它逼你把数据洗干净。

## 上手四步

1. 先确认格式合法性。用 `xmllint --noout file.xml` 做良构检查，报错行号会直接指出标签不匹配或缺闭合。
2. 声明并校验 Schema。在根元素上写 `xsi:schemaLocation`，再用 `xmllint --schema schema.xsd file.xml` 验证结构。
3. 用 XPath 定位数据。比如 `//order/item[@qty>1]`，先在命令行或用小脚本试通表达式，再写进代码。
4. 解析时关闭外部实体。解析器默认可能加载 DTD 与外部实体，存在 XXE 风险；显式禁用 DTD 加载和外部实体解析，以所用库的官方文档为准。

## 常见问题

**XML 和 HTML 有什么区别？**
HTML 有预定义标签，浏览器容忍错误；XML 标签自定义，且要求严格良构，一个未闭合标签就是致命错误。XHTML 曾试图把两者结合，但没有成为主流。

**属性还是子元素？**
经验规则：元数据、ID、单位这类短小且不重复的值放属性；可能重复、可能扩展、需要顺序的内容放子元素。规范本身不强制。

**XML 会被 JSON 完全取代吗？**
不会在短期内发生。JSON 没有命名空间和内置校验标准，在跨组织契约和文档格式领域，XML 的生态仍有优势。新项目做 Web API 时优先 JSON 是合理的。

**解析大文件有什么注意点？**
不要一次性把整个文档读进内存。用流式解析（如 SAX 或各语言的 StAX 类接口）逐节点处理，内存占用可控。具体 API 以对应库的官方文档为准。
